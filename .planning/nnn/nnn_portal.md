# nnn as the default file explorer

Folders opened from GUI programs, and file open, folder and save dialogs, run nnn in the styled wrapper window. Notes moved here from the todo. `nnn.desktop` expands `$HOME` through `sh -c` since 2026-11-14, so the repo has no user path in it; programs that run the `xdg-open` command do not open it (confirmed: the Minecraft launcher's folder button), which the user accepted (see "Result of the 2026-11-14 change").

## Folder opening

- No other file manager is installed, so `inode/directory` resolves to `nnn.desktop` only. The package's entry ran plain `nnn`, and `xdg-open` ignores `Terminal=true`, so a GUI program's "open folder" ran nnn with no terminal (`xdg-open /tmp` printed `0 entries` and opened nothing).
- `symlinks/home_@user@_.local_share_applications_nnn.desktop` overrides it with `Terminal=false` and an `urxvt -name wrapper -e …/nnn-wrap.sh %f` command. Until 2026-11-14 the path in it was `/home/lenny/.config/herbstluftwm/scripts/nnn-wrap.sh`. Checked live with that line: `xdg-open /tmp` opened a styled nnn window.
- Current, since 2026-11-14 (reverted for retests and restored the same day; before that the path was `/home/lenny/.config/herbstluftwm/scripts/nnn-wrap.sh`): `Exec=urxvt -name wrapper -e /bin/sh -c "exec \\"\\$HOME/.config/herbstluftwm/scripts/nnn-wrap.sh\\" \\"\\$@\\"" sh %f`, quotes and `$` escaped twice as the desktop-entry spec requires. It passes `desktop-file-validate` and GLib's parser reads it correctly (`Gio.DesktopAppInfo.launch_uris` with a stub `urxvt` gave the right arguments, with and without a folder). Checked live: VS Code and the other programs listed below open nnn and Bambu Studio's Open Project works, but **`xdg-open /tmp` opens no window** and the Minecraft launcher's folder button opens nothing.
- Since 2026-11-14 (WP7, `scripts/tui-wrap.sh` replaced the `urxvt -name wrapper -e` command everywhere): `Exec=/bin/sh -c "exec \\"\\$HOME/.config/herbstluftwm/scripts/tui-wrap.sh\\" \\"\\$HOME/.config/herbstluftwm/scripts/nnn-wrap.sh\\" \\"\\$@\\"" sh %f`, escaped twice as before. Checked: `desktop-file-validate` exit 0; the line read through `GLib.KeyFile` and `GLib.shell_parse_argv`, with `%f` replaced after parsing, runs `tui-wrap.sh` with `nnn-wrap.sh` and the folder as separate arguments (a name with a space stays one argument) and without a folder. Not checked live. It has the same shape as the line above, so the `xdg-open` limitation is unchanged. `nnn-portal.py` now starts `tui-wrap.sh --title TITLE nnn-wrap.sh --pick …`; its `NNN_PORTAL_TERMINAL` override is gone (nothing in the repo used it).
- Why `xdg-open` fails (xdg-utils 1.2.1, `search_desktop_file` in `/usr/bin/xdg-open`, reproduced with a stub `urxvt` on `PATH`): it does not implement the spec's quoting. `first_word` and `last_word` use `read` without `-r` ("handles backslashes but not quote marks"), the first word is looked up with `command -v`, the rest is split on whitespace with `set -- $(…)`, and the command runs as `env "$command" "$@"`. An argument can therefore never contain a space, and the stub received `<-c> <"exec> <\"\$HOME/…\"> <\"\$@\"">`. `sh -c` gets `"exec` as its script and exits at once.
- The desktop-entry spec (fetched 2026-11-14): no expansion of environment variables or `~` in `Exec`, `Path` or `TryExec`; `$` and `~` are reserved characters that force double quotes; the first word is a full path or a name looked up in the desktop environment's `PATH`; `TryExec` is only a presence check and `Path` only sets the working directory. An `Exec` line that works for GLib and for `xdg-open` has to be flat words with no user name in it.
- The D-Bus activation file `symlinks/home_@user@_.local_share_dbus-1_services_org.freedesktop.impl.portal.desktop.nnn.service` was changed the same way and kept: `Exec=/bin/sh -c 'exec "$HOME/.config/herbstluftwm/scripts/nnn-portal.py"'`. `xdg-open` does not read it. The D-Bus spec defines no quoting for `Exec` ("similar to desktop entries"), GLib's parser reads the line correctly, but the sandbox could not test dbus-daemon's own parser (it cannot create a bus socket), so it was checked live on 2026-11-14: after `pkill -f nnn-portal.py` and `busctl --user introspect org.freedesktop.impl.portal.desktop.nnn /org/freedesktop/portal/desktop`, `pgrep -af nnn-portal.py` showed `python3 /home/lenny/.config/herbstluftwm/scripts/nnn-portal.py` running, so D-Bus started the portal through this line and `$HOME` expanded. A file dialog served by that newly started process was not recorded separately.
- A session load ignores the `PATH` argument, so `nnn-wrap.sh`, given a folder, starts nnn with `-s startup -P o`, where `o` is an inline `NNN_PLUG` command writing `+c<folder>` to nnn's plugin pipe (`+` is the first inactive context after the current one). Checked live: the folder opens in context 5 and nnn switches to it. Contexts 1 to 4 still hold the session. The plugins folder must be a working link (`~/.config/nnn/plugins` to `/usr/share/nnn/plugins`, see the "nnn plugins" quickstart step); a dangling link made the plugin fail with "no such file or directory".
- `nnn-wrap.sh` stops with "DOTFILES_DIR is not set" without that variable (`startup.autostart` exports it with `hc export`). A herbstluftwm session started before that line was in place needs `herbstclient reload` (or a new login), or the keybind and `xdg-open` both fail. Seen 2026-11-14: the session started on `main` and the branch was checked out three minutes later.
- How Obsidian reaches nnn (traced 2026-11-14 with `busctl --user monitor`): Obsidian 1.15.0 (an AppImage, Electron 43.8.4, with the same `FileManager1`, portal `OpenURI` and `xdg-open` code as VS Code) calls the portal's `OpenURI.OpenDirectory`; the portal calls `FileManager1.ShowItems`, which has no owner here (no file manager installed); the portal's own docs then say it "falls back to the `OpenURI` method on the directory", so the portal itself launches `nnn.desktop` from its own process, not from the session. That process needs `DOTFILES_DIR` for `nnn-wrap.sh`. A portal that started before `DOTFILES_DIR` was exported keeps its old environment, so the launch stopped at "DOTFILES_DIR is not set" in a window that closed at once. The systemd user environment already had the variable (`systemctl --user show-environment`; `dbus-update-activation-environment DOTFILES_DIR` does reach it), the running process did not. Restarting the portal fixed it. A fresh login starts the portal after `startup.autostart` has exported the variable, so this should not recur; after changing what `startup.autostart` exports, restart the portal (`systemctl --user restart xdg-desktop-portal`). The AppImage's `AppRun` was also read (it puts its directory first in `PATH` and sets `XDG_DATA_DIRS` and `LD_LIBRARY_PATH` into the mount) and was not the cause.
- VS Code's "Open Containing Folder" asks the portal first, and GLib found no handler for folders (the user-level `nnn.desktop` shadows the package's, and the user `mimeinfo.cache` did not list it), so an empty "Open With" chooser appeared before the `xdg-open` fallback. Fixed by `update-desktop-database ~/.local/share/applications`, now run by the quickstart's "Link config files" step. Checked live: it opens straight in nnn, for "Open Containing Folder" and for the command palette's "Open Logs Folder" and similar commands.

## Result of the 2026-11-14 change

The `.desktop` file was changed to expand `$HOME` through `sh -c`, and the user tested every program installed by the quickstart's package list with it in place. It was then reverted to the absolute path for retests and restored the same day. Decision (the user, 2026-11-14): keep the `sh -c` form and accept that programs which run the `xdg-open` command do not open nnn.
- Minecraft launcher: its folder button opens nothing with the quoted line and opens nnn with the absolute path. Cause confirmed: `~/.minecraft/launcher/liblauncher.so` (`SystemUtils_Linux.cpp`) holds the strings `/usr/bin/xdg-open "` and `: error `, so it runs `/usr/bin/xdg-open "<folder>"` by absolute path, and its log shows `Running method openDirectory` nine times between 18:02:07 and 18:02:15 (the user clicking while nothing opened). Accepted by the user.
- Bambu Studio: "Open Project" on the first screen hung once on the first test (its log for that run, 17:37, stops growing at 17:37; the logs are encrypted, `*_enc_dc.log.0`, so the cause is unknown). It did not hang with the quoted line in a scratch `XDG_DATA_HOME` (`XDG_DATA_HOME=/tmp/claude-1000/bambu-repro bambu-studio`, a `nnn.desktop` copy plus `update-desktop-database`), nor with the quoted line live in the real file. A one-off, not explained.
- Obsidian "show in file explorer": nothing with either version at first, not caused by the change. Cause found 2026-11-14: see "How Obsidian reaches nnn" above. Fixed by `systemctl --user restart xdg-desktop-portal`.
- Dunst: nothing with either version, and ignored by the user as a very rare use. Its context menu needs `dmenu` (`/etc/dunst/dunstrc:264`), which is not installed (`command -v dmenu` finds nothing, only rofi exists), and `browser = /usr/bin/xdg-open` (line 267) is only reached through that menu. Peek works when it is set to open the location automatically.
- Not tested: folder-opening actions of the other programs whose files hold an `xdg-open` string or a Qt launcher list (Blender, FreeCAD, Krita, Orca Slicer, Inkscape, Peek, Xarchiver; see below). Only their file dialogs were tried. If one of them is needed, it will not open nnn through `xdg-open`.

Options for removing the hard-coded path that were looked at and not taken:
- Keep the absolute path (`/home/lenny` stays in the repo).
- Generate the file at install with the real path (a template, a generator, a quickstart step, `.gitignore` entries; a fresh clone has no file until the step runs).
- A launcher at a fixed path in `/usr/local/bin`, installed through `symlinks/` and finding the scripts from its own location (needs `readlink -f` because `nnn-wrap.sh` uses `dirname "$0"`; a user-writable file on root's `PATH` is a new exposure on a world-writable mount, see SEC-1 in the script review). This is the only option that would also make `xdg-open` callers work without the absolute path.
- Put the scripts folder on `PATH` from `startup.autostart`: only reaches processes that inherit herbstluftwm's environment, not D-Bus-started ones. Ruled out.

## File open and save dialogs

Built as our own portal backend, no new package. VS Code's "Open Folder" is a `GtkFileChooserDialog` served by `xdg-desktop-portal-gtk`, so the portal's FileChooser backend had to be replaced, not a launcher.
- `scripts/nnn-portal.py` (Python, Gio) owns `org.freedesktop.impl.portal.desktop.nnn` and implements `OpenFile` and `SaveFile`. Each dialog runs `nnn-wrap.sh --pick file|dir|save OUT START [NAME]` in the urxvt wrapper window; nnn writes the chosen path to OUT, which is gone or empty on a cancel (replied as cancelled). The startup session is loaded and the application's `current_folder` opens in the first inactive context (`-P o`).
- Keys in picker mode: Enter picks a file or the selection, `;p` (or Alt+p) picks the folder shown (dir dialogs), `;s` (Alt+s) asks for a file name, prefilled, in the folder shown (`scripts/nnn-pick-save.sh`, which ends the pick with the plugin pipe's `0p`).
- Registration, linked from `symlinks/`: the D-Bus activation file, `/usr/share/xdg-desktop-portal/portals/nnn.portal`, and `~/.config/xdg-desktop-portal/portals.conf` (FileChooser prefers `nnn;gtk`). The portal does not fall back to gtk when the backend fails at runtime.
- Checked live: VS Code's File > Open Folder works, with contexts 1 to 4 populated, and cancelling no longer hangs VS Code (a cleanup crash on a missing output file was not sending the reply).
- Checked live since: Open File, Open Folder and Save As (`;s`) all work. Vivaldi and Rambox open the right folder from the downloads list, and Vivaldi's Open File uses nnn. `SaveFiles` (several files at once) is not implemented: nothing known calls it (`libportal` is not installed), held off.
- Which apps reach it depends on the app. `startup.autostart` exports `GTK_USE_PORTAL=1` and `QT_QPA_PLATFORMTHEME=xdgdesktopportal` (`hc export`, so everything herbstluftwm starts has them), which sends GTK native choosers and Qt native dialogs through the portal. Checked with xprop and by trying each app, with the variables confirmed in the running processes:
  - nnn: VS Code, Vivaldi, Rambox (portal); Orca Slicer, Sublime Text (GTK native chooser); FreeCAD (Qt native dialog); Krita once Settings > Configure Krita > General > Miscellaneous > "Enable native file dialogs" is ticked (checked live; a per-app setting, greyed out in AppImage builds, this is the Arch package).
  - Own dialog, the variables do not help: Inkscape (plain `GtkFileChooserDialog`; known to ignore `GTK_USE_PORTAL`, see upstream issue inkscape/inbox 783), Bambu Studio (statically linked wxWidgets references only `gtk_file_chooser_dialog_new`, where Orca's references `gtk_file_chooser_native_new`), Blender (draws its own file browser).
- Fresh install: after "Link config files" the D-Bus services folder did not exist when the session bus started, so the bus config needs a reload (`busctl --user call org.freedesktop.DBus /org/freedesktop/DBus org.freedesktop.DBus ReloadConfig`) and the portal a restart (`systemctl --user restart xdg-desktop-portal`) once. The quickstart's "Link config files" step now does both when a session bus is running (syntax checked, not run on a fresh install).
